# ERDL 运算符覆盖度全量分析

> ⚠️ **历史文档（已过时）**：本文档是 v1.1 时代（13 运算符）的覆盖分析。其建议扩展的运算符（starts_with / ends_with / length_* / between / count_* 等）**已全部在 ERDL v2.0/v2.1 落地**——当前为 30 运算符（28 条件 + 2 修饰符，见 [erdl-language-spec-v2.1](./SPEC/erdl-language-spec-v2.1.md) §5.2）。本文档仅作历史留档，非当前权威。

## 方法论

对标企业人力资源管理，Agent 的"职业行为"可分解为以下维度：

### 一、操作类型维度（WHO + WHAT）
- 谁在操作（Agent身份、角色、部门）
- 用了什么工具（tool.name）
- 对什么目标（文件路径、数据库表、API端点、命令）

### 二、参数约束维度（HOW）
- 参数类型是否正确
- 参数值是否在允许范围内
- 参数格式是否合法
- 参数大小是否在限制内

### 三、时间维度（WHEN）
- 操作频率（rate limiting）
- 时间窗口（within）
- 操作顺序/依赖（sequence）
- 时间段约束（business hours, maintenance window）

### 四、上下文维度（CONTEXT）
- 前置状态（之前是否做了某个操作）
- 环境条件（生产/测试环境）
- 风险累积（连续错误次数、置信度衰减）

### 五、合规维度（COMPLIANCE）
- 数据分类（是否涉及PII/GDPR）
- 管辖权（EU/CN/US）
- 审批链路（是否需要人工确认）
- 审计要求（操作是否被记录）

### 六、纠偏维度（CORRECTION）
- 自动修正能力
- 替代方案建议
- 降级路径

## 当前 SPEC v1.1 的 13 个运算符（覆盖分析）

| 运算符 | 覆盖维度 | 缺口 |
|--------|---------|------|
| eq | 一（精确匹配） | 无 |
| ne | 一（排除匹配） | 无 |
| gt/gte/lt/lte | 二（数值范围） | 只能比较数值，不能比较日期/时间/版本号 |
| in | 一（白名单/黑名单） | 只能精确列表，不能模糊列表 |
| not_in | 一（排除列表） | 同上 |
| contains | 二（子串匹配） | 无法区分前缀/后缀/中间包含 |
| not_contains | 二（子串排除） | 同上 |
| match | 二（正则匹配） | 无法做结构化匹配（如URL解析、路径解析） |
| exists | 二（字段存在性） | 只能判断是否存在，不能判断非空/类型/格式 |
| within | 三（时间窗口） | 只能单条件时间窗口，不能复合时间逻辑 |

**覆盖率评估：约40%。** 缺失的是：
1. 字符串边界匹配（starts_with/ends_with）
2. 长度/大小约束（length_*/size_*）
3. 类型检查（type_of）
4. 范围匹配（between, not_between）
5. 版本/日期比较
6. 数值/集合运算（count, sum, any, all）

## rulsynor-core 已实现的扩展（7个）

| 运算符 | 覆盖维度 | 合理性 |
|--------|---------|--------|
| starts_with | 二（路径前缀、协议头） | ✅ 必须。文件路径、URL前缀是最常见的约束 |
| ends_with | 二（文件后缀、扩展名） | ✅ 必须。数据库drop、文件类型过滤 |
| not_exists | 二（字段缺失检测） | ✅ 必须。exists的对称，安全默认 |
| length_gt/gte/lt/lte/eq | 二（长度限制） | ✅ 必须。payload大小、命令长度、内容上限 |

## 需要新增的运算符（穷举分析）

### A类：字符串/格式匹配（高频、必须）

| 运算符 | 说明 | 场景 | 优先级 |
|--------|------|------|--------|
| starts_with | rulsynor已有 | /etc/, https://, DROP | P0 |
| ends_with | rulsynor已有 | .sh, .sql, .env, '.js' | P0 |
| not_starts_with | 取反边界 | 不允许非白名单路径 | P1 |
| not_ends_with | 取反边界 | 不允许非白名单后缀 | P1 |

### B类：长度/大小（高频、必须）

| 运算符 | 说明 | 场景 | 优先级 |
|--------|------|------|--------|
| length_gt/gte/lt/lte/eq | rulsynor已有 | 10MB写入拦截、命令长度>5000告警 | P0 |
| size_gt/gte/lt/lte | 文件大小（bytes） | 单文件上传限制 | P1 |
| count_gt/gte/lt/lte | 集合元素个数 | API调用次数、同时打开连接数 | P1 |

### C类：类型检查（中频、生产必需）

| 运算符 | 说明 | 场景 | 优先级 |
|--------|------|------|--------|
| type_of | 值类型检查 | 期望number但收到string | P1 |
| is_null | 显式null检查 | 不同于exists（区别null和undefined） | P2 |
| is_blank | 空白值检查 | 空字符串、纯空格 | P2 |

### D类：范围匹配（中频）

| 运算符 | 说明 | 场景 | 优先级 |
|--------|------|------|--------|
| between | 数值/日期在范围内 | 金额 1000-5000、时间 9:00-18:00 | P1 |
| not_between | 范围外 | 非工作时间禁止敏感操作 | P1 |

### E类：语义匹配（高频、与HR概念对齐）

| 运算符 | 说明 | 场景 | 优先级 |
|--------|------|------|--------|
| permission_level | 权限等级检查 | 部门经理 vs 普通员工的操作范围 | P0 |
| role_has | 角色能力检查 | Agent是否具备执行该操作的资质 | P0 |
| is_production | 环境判断 | 生产环境额外限制 | P1 |

### F类：顺序/依赖（未来，与HR"考核"对齐）

| 运算符 | 说明 | 场景 | 优先级 |
|--------|------|------|--------|
| after | 时序依赖 | 必须先读文件才能修改文件 | P2 |
| before | 时序前置 | 修改前必须备份 | P2 |
| depends_on | 依赖检查 | 必须通过测试才能部署 | P2 |

### G类：模式/语义（未来）

| 运算符 | 说明 | 场景 | 优先级 |
|--------|------|------|--------|
| matches_schema | JSON Schema匹配 | 验证Agent输出结构的正确性 | P2 |
| semantic_similar | 语义相似度 | 命令意图是否与允许的意图一致 | P3 |

## 推荐升级方案

### SPEC v1.2 Operator 扩展

**P0（本版必须加入，15个）：**

SPEC v1.1 的 13 个 + 新增 2 类：

1. **字符串边界匹配**：`starts_with`, `ends_with`, `not_starts_with`, `not_ends_with`
2. **长度约束**：`length_gt`, `length_gte`, `length_lt`, `length_lte`, `length_eq`
3. **范围匹配**：`between`, `not_between`
4. **元素计数**：`count_gt`, `count_gte`, `count_lt`, `count_lte`

理由：这些都是现有规则已经需要的，而且是对标数据验证领域标准（JSON Schema、OWASP输入验证）的最小完备集。

**P1（下一版，6个）：**

`type_of`, `is_null`, `is_blank`, `size_*`, `permission_level`, `role_has`

理由：与HR概念（角色、权限、资质）直接对齐，是"职业化"的核心。

**总数：13 → 27 → 33**

## 与HR管理模型的对齐

| HR概念 | 运算符体现 |
|--------|----------|
| 岗位职责 | `tool.name` + `eq`/`in` — 只能做你岗位内的事 |
| 能力评估 | `role_has` — 你有没有资质做这件事 |
| 权限级别 | `permission_level` — 你的级别能否批这个 |
| 工作量限制 | `length_*`, `count_*`, `size_*` — 不能一次干太多 |
| 时间管理 | `within`, `between` — 工作时间、频率限制 |
| 绩效指标 | `gt`/`lt` — 阈值告警（交易额>5000需审批） |
| 行为规范 | `contains`, `starts_with` — 不能访问系统目录 |
| 纠偏辅导 | `CORRECT` — 错了一次自动修正，三次才升级 |
| 档案管理 | `exists`, `not_exists` — 完整记录才放行 |
| 安全红线 | `match` — `rm -rf` 零容忍 |

---

## 结论

SPEC v1.1 的 13 个运算符是**v1.0 的最小可行集**——当时只考虑"能不能比较"。现在 rulsynor-core 的工程实践告诉我们：**规则引擎需要的是完整的约束表达能力**。

不是 SPEC 错了。是实践推进了认知。

建议：立即启动 SPEC v1.2 升级，P0 扩展 15 个运算符，11 月冻结。
